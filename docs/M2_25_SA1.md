# M2.25 — SA-1: it boots, and it is worth 1.73x from ROM, 2.92x from I-RAM

The SA-1 was chosen over the software levers in M2.24. Before designing a
two-processor split, two things had to be established: that the chip works at
all under this toolchain, and what it is actually worth once its data is where
the port would have to put it. Both are now measured.

---

## 1. It boots

`src/sa1_probe.s` + `tools/verify_sa1.lua`:

```
frames=30 magic=5AA1 sa1_ctr=DB->D3 scpu_ctr=63->36
RESULT OK - SA-1 boots and shares I-RAM with the S-CPU
```

The S-CPU writes the SA-1's reset vector to CRV (`$2203`), clears RESB in CCNT
(`$2200`), and the SA-1 starts. Calypsi has no SA-1 target and does not need
one: the SA-1 *is* a 65816, so `--core 65816` output runs on it unmodified. What
the port has to build is the memory map, the boot handshake and the split — not
a compiler backend.

Four things cost time here and are worth writing down:

* **I-RAM is write-protected at reset.** SIWP (`$2229`) and CIWP (`$222A`) both
  come up as `0`, which permits no writes from *either* processor. A store to
  I-RAM before they are opened is silently dropped — no fault, no side effect,
  the value simply does not land. `$FF` to each opens all 2KB.
* **SA-1 cartridges are LoROM-shaped**, not HiROM: 32KB banks at `$8000-$FFFF`,
  header at file offset `$7FC0`. Map mode `$23`, chipset `$34`. The port's HiROM
  layout and `pack_hirom.py` do not carry over; `tools/pack_lorom.py` is the
  SA-1 side.
* **Mesen does not route I-RAM through `emu.memType.snesMemory`.** Reading
  `$3000` on the S-CPU bus returns open-bus garbage while both processors are
  using it correctly. `emu.memType.sa1InternalRam` is the one that works.
* **The SA-1 reaches nothing in `$7E/$7F`.** All 34KB of game state has to move
  to BW-RAM. This is the single fact that makes the migration a port rather than
  a recompile.

## 2. What it is worth

`src/sa1_bench.s` runs one identical, branch-free instruction stream — modelled
on what Calypsi emits for `sprite_collide`: `long:` accesses, `rep`/`sep` width
churn, register moves — in four places, one at a time, never overlapping.

| run | | frames | eff. MHz | vs run A |
| --- | --- | --- | --- | --- |
| A | S-CPU, arrays in WRAM `$7E` | 38 | 3.34 | 1.00x |
| B | SA-1, arrays in I-RAM | 22 | 10.74 | 1.73x |
| C | SA-1, arrays in BW-RAM | 22 | 10.74 | 1.73x |
| D | SA-1, arrays in BW-RAM, **code copied into I-RAM** | 13 | 10.74 | **2.92x** |

Three conclusions, and the third is the design:

* **B = C exactly. Data placement is free.** BW-RAM costs nothing against I-RAM,
  so moving 34KB of game state onto the cartridge is not the problem it looked
  like. The 2KB of I-RAM does not need to hold *data*.
* **C vs D is instruction fetch, and it is the whole deficit.** The same
  instructions cost 3.93M cycles fetched from ROM and 2.32M fetched from I-RAM —
  **69% overhead**, which is why a 3.2x clock ratio delivers 1.73x. The 2KB of
  I-RAM is therefore a *code* budget, and it is the most valuable 2KB on the
  cartridge.
* **The S-CPU keeps FastROM.** Run A measures 3.34MHz on the SA-1 cartridge,
  identical to a plain FastROM cartridge, so nothing left on the S-CPU gets
  slower. This was a real risk — the SA-1 map mode has no FastROM bit in the
  header — and it is settled: MEMSEL still works, for banks `$80-$FF`.

Two measurement traps this went through, both of which produced confident wrong
numbers first:

* **Run A was timed at 2.66MHz** until it was moved to bank `$80`. FastROM
  applies only to banks `$80-$FF`; MEMSEL does nothing for code in bank `$00`.
  The benchmark ran in bank `$00` while the port it is compared against runs at
  `$C0`, which inflated every SA-1 ratio by a quarter (2.09x reported where the
  truth was 1.73x).
* **Run B measured as never having happened**, because a single phase counter
  stepped `2` then `3` on consecutive instructions and the frame-boundary
  sampler could never observe the intervening value. One marker byte per run.

Bus contention was checked separately by replacing the S-CPU's `stp` with a spin
loop: every figure above was unchanged to the frame. That is Mesen's model
rather than hardware, so it is a reason not to worry rather than a proof.

## 3. What this means for the port

The levels that motivated all this need far less than the ceiling:

| | frame budget used | needs |
| --- | --- | --- |
| `cycles` | 86.8% | 1.15x |
| level 12 | 85.9% | 1.16x |
| `xstep` | 79.1% | 1.26x |

**1.73x clears all of them with room, without any I-RAM overlay.** So the first
implementation is the simple one — game code runs on the SA-1 straight out of
ROM, state in BW-RAM, S-CPU keeps the PPU — and the I-RAM code overlay stays in
reserve as a second 1.7x for whatever still does not fit.

`xmaschallenge` at 23.4% needs 4.3x and is not an SA-1 problem; it is the
separate pre-existing defect noted in M2.24 and stays on its own track.

## 4. C runs on it, and the ROM layout survives

Two more things were unknown and are now settled.

**Calypsi C runs on the SA-1 unmodified.** `src/sa1_ccheck.c` computes four
checksums with values known ahead of time - not captured from a first run, which
would have locked in whatever a broken map produced - and all four match:

```
BW-RAM zeroed globals    got FD00  want FD00  ok
BW-RAM initialised data  got 018C  want 018C  ok
ROM constants            got 0E10  want 0E10  ok
```

The hookup is one detail: cstartup declares `__program_root_section` (the word at
`$FFFC`) and `__program_start` as `.pubweak`, so a strong definition in
`src/sa1_boot.s` takes the reset vector for the S-CPU while cstartup's entry
becomes the *SA-1's*. The C runtime is then initialised by the processor that
uses it, and none of it had to be rewritten.

It does need a stub in front of it. cstartup sets the stack pointer and
immediately `call`s `__low_level_init`, which pushes - and the SA-1's stack is in
the BW-RAM window, which comes up write-protected along with I-RAM. Those pushes
would be dropped and the first `rts` would return into nothing. `sa1_entry`
opens CIWP/CBWE before cstartup runs a single instruction; `__low_level_init` is
already too late.

**The port's HiROM layout works on the SA-1 unchanged.** This was the last thing
that could have forced a re-layout of 1.9MB. `src/sa1_rommap.c` reads it off the
chip - `pack_lorom.py --stamp` writes each 32KB block's own index into the
padding, so an address reply names the part of the ROM that answered:

```
$C04000  -> block  0   $C44000 -> block  8   $D04000 -> block 32
$C0C000  -> block  1   $C84000 -> block 16   $DC4000 -> block 56
```

`$C0-$DF` is a **linear 2MB HiROM window** at the Super MMC's reset values, so
bank `$C0+n` is ROM offset `n * $10000` - exactly what the port already builds.
Code at `$C0-$C2`, sprite CHR at `$C3`, levels at `$C4-$C9`, BG CHR at `$CA`:
all of it stays put, and no bank switching is needed at all. `$00-$3F:$8000` is
LoROM-shaped over the same ROM (bank `B` -> offset `B * $8000`), and `$80-$BF`
and `$E0-$FF` are mirrors.

So the ROM side of the migration is nearly free. Two things move:

* the **header** goes to file offset `$7FC0` and the reset vector to `$7FFC`,
  because the SA-1 map is LoROM-shaped, where the port puts them at `$FFC0`;
* the first 32KB of bank `$C0` becomes a boot block holding the S-CPU's boot,
  the SA-1 entry stub and the header. It currently holds `farcode`, so this is a
  linker-config change.

The SA-1 starts with program bank 0, and `$00:8000-$FFFF` is the same physical
ROM as `$C0:0000-$7FFF`, so the entry stub is reachable from both views and can
`jmp long:` into the `$C0` code.

Everything that actually moves is RAM.

## 5. The whole game links, and runs, on the SA-1

`SA1=1 sh tools/build_game.sh` relinks **the same object files** the HiROM ROM
is built from against `out/snes-SA1-full.scm`, and packs a 1,900,544-byte
cartridge - the full 168-level set. It linked without a single placement error,
which is the payoff of the ROM layout surviving: only the RAM moved.

Where it moved to, from `out/game_sa1.map`:

| | | used |
| --- | --- | --- |
| DirectPage | I-RAM `$0000-$00FF` | 19.5% |
| IRamShared | I-RAM `$0100-$07FF` � the mailbox | 0%, nothing claims it yet |
| NearRAM | BW-RAM window `$6000-$7FFF` � stack, near data | 50% (4KB of 8KB) |
| FarRAM | BW-RAM linear `$402000-$40FFFF` | 59.2% (34KB of 56KB) |

Headroom everywhere. `oam_buf` lands at `$4081DB` and `drawing_frame` at
`$40851F`; the boot block moved to the bottom half of `$C0`, and the reset
vector points at `scpu_boot` rather than cstartup, which is the `.pubweak`
override doing its job.

Running it (`tools/verify_sa1_game.lua`):

```
SA-1 seen in 33 distinct code sites
BW-RAM holds initialised state: true
drawing_frame took 1 distinct values over 40 frames
```

So the C runtime initialises the game's state where the new map put it, and game
code executes across the whole ROM - but **no frame ever completes**, and that is
exactly right for this point. `drawing_frame` is incremented at the end of
`ppu_wait_nmi()`, and the entire PPU path is still compiled into the SA-1's half,
where every register write goes nowhere. The SA-1 sits in `chr_flush`, pushing
CHR at a VRAM port it cannot reach.

The verifier asserts that state deliberately rather than calling it a failure,
and says so in its verdict - when the split lands, the pass condition becomes
"frames advance" and today's state becomes the failure.

### The handshake, and what it cost to find

The frame boundary is now split. `ppu_wait_nmi()` on the SA-1 publishes a
sequence number into the I-RAM mailbox and spins; the S-CPU, once per vblank,
reads the pads and echoes the number back. `tools/verify_sa1_game.lua`:

```
drawing_frame advanced 120 times in 120 video frames after boot settled (100% of 60Hz)
RESULT OK - the game runs on the SA-1, its state is in BW-RAM, and the S-CPU
            handshake is pacing frames
```

A sequence number rather than a flag, because this is not a lock added to an
existing rhythm - it *is* the rhythm. There was no frame pacing on the SA-1 at
all, so the SA-1 waits for equality rather than for an edge and a missed vblank
costs a frame instead of desynchronising the two.

Three source files differ between the ROMs, all for the same reason - they touch
registers the SA-1 cannot reach:

| | |
| --- | --- |
| `shim_ppu.c` | `ppu_wait_nmi` becomes the handshake |
| `shim_core.c` | `pad_poll` reads the mailbox instead of `$4218` |
| `snes_main_full.c` | `level_select` has its **own** copy of the frame boundary |

That third one is worth naming: the menu polls `HVBJOY` and reads the pads
itself, so fixing `ppu_wait_nmi` alone left the game spinning in the menu
forever on input it could never read. A seam that exists twice has to be found
twice.

Two mistakes, both the same shape - an address that is valid on both sides but
means different things:

* **The two processors see I-RAM at different addresses.** The SA-1 has it at
  `$0000-$07FF` *and* `$3000-$37FF`; the S-CPU has it **only** at `$3000-$37FF`.
  The C side's mailbox at `$0100` is `$3100` from the assembly. Using `$0100` on
  both sides does not fault - it reads WRAM `$0100`, a perfectly valid address
  holding something else - so the SA-1 sat in `ppu_wait_nmi` waiting for an echo
  that was being written somewhere else entirely.
* **The frame rate was first measured at 28%** because the sampling window
  started at power-on, and boot - building the level select, the first CHR
  uploads - completes very few frames. The steady-state figure is 100%. The
  verifier now discards the first 60 frames and says so.

### The push, and where it actually stands

The S-CPU now runs the shim's **own C flush code** rather than a hand-written
copy, which is possible because it can read BW-RAM linearly at `$40:xxxx` -
measured, not assumed. `shim_scpu_frame()` does screen state, any pending
one-off request, the menu transfer, then scroll/CGRAM/VRAM/OAM/CHR.

**Working:** boot, 60Hz pacing, the level select fully drawn, controller input,
and selecting a level.

**It plays.** `tools/verify_sa1_play.lua` drives the ROM the way a player does -
waits for the level select, presses A, and then checks the things that can only
be true if the whole split works:

```
left the menu:         true
frame rate in-level:   657/660 (100% of 60Hz)
BG1 tilemap written:   424/4096 tiles
CGRAM matches PAL_BUF: true
scroll_x moved:        true (547 -> 600)
RESULT OK - the SA-1 build plays
```

Screenshotting the SA-1 build beside the HiROM build at the same point settles
it: they are the same picture. That comparison is what ended the hunt, and it
should have been the FIRST thing done rather than the last - two of the three
"faults" chased before it were artefacts of measuring, not of the port.

**The bug that made it look dead was the pads.** The game reads a button in
exactly one place: `ppu_wait_nmi` calls `pad_poll(0)` and `pad_poll(1)` every
frame, which is why every `pad_poll()` in `SAUCE/` is commented out. Those two
calls sat inside the `#else` of the SA-1 branch, so **gameplay saw no input at
all**. The level select still worked, because it polls for itself - so menus
responded, levels loaded, the picture was correct, the frame rate was 60Hz, and
the cube simply could not jump. It died on the first obstacle, restarted, and did
it again forever: "loads a level and sits there doing nothing."

Moving the calls into the SA-1 branch then broke the *menu*, because
`level_select` polls again right after `ppu_wait_nmi` and a second poll destroys
the press edge - `press` is `now & ~was`, and the second call sees the button
already held. The redundant poll came out.

That pair is worth remembering as one lesson: **the frame boundary owns the pad
read, and exactly one place may do it.**

One other real defect stood in the way, and it is the same shape as
the `menu_flush` one: **the game calls the flush entry points itself**.
`flush_vram_update2()` after building the first screen, `flush_chr_now()` after
a bank switch. Run on the SA-1 they emptied `vq_len`, `cq_len` and the CHR queue
without moving a byte, so the level's first screen was discarded. Both are now
requests to the S-CPU, which keeps the caller's contract - the queue really is
empty when they return.

That change needed prototypes for the new `shim_scpu_*` entry points. Without
one, `--code-model large` assumes a NEAR call and emits a `jsr` to a function in
another bank: no link error, wrong target.

**I reported a 3% frame rate before finding any of this, and it was wrong.** The
figure came from differencing `drawing_frame`, which is a byte, across 600
frames: 530 increments read back as 18 after wrapping. Counting transitions
gives 99%. That is the same error as the boot-window one earlier on this page,
and acting on it sent me looking for a stall that was never there.

Two other measurement dead ends worth recording: Mesen's exec-range memory
callbacks do not fire for `emu.cpuType.sa1` (they return no hits at all), and
`emu.eventType.scanline` does not exist. Per-frame PC sampling from `endFrame`
is what works, and 2100 samples was enough to show 99.4% of the SA-1's time is
spent blocked in `ppu_wait_nmi` - which is the handshake working, not a stall.

**This is not playable yet, and the milestone above should not be read as
saying otherwise.** `verify_sa1_game` passes on menu behaviour; it does not
enter a level, so it does not cover this.

Six defects were found and fixed getting this far, and five were the same
shape - something true on one processor and not the other:

* **I-RAM is at different addresses per CPU** (`$0000` for the SA-1, `$3000`
  for the S-CPU). Hit twice: once in assembly, once in C. Neither faults; both
  silently use WRAM instead.
* **I-RAM is not zeroed at power-on.** `boot_ack` came up as `$86`, so
  `!boot_ack` was false and `video_init` never ran - the screen showed
  uninitialised VRAM while everything else worked.
* **`menu_flush` was called on the SA-1**, where its DMA moves nothing but its
  `menu_dirty` guard still cleared - so the S-CPU's copy always found the menu
  clean. The backdrop, palette and cleared tilemap all drew correctly, which
  made it look like a missing font.
* **`ppu_off()` only reaches the shadow**, so the S-CPU has to apply screen
  state *before* any bulk transfer. Without that, the 4KB font upload ran with
  the screen on, overran vblank, and the hardware dropped the tail.
* **The budgeted CHR upload ran before the menu's transfer**, pushing a
  deadline-bound write past the end of vblank.

And one in the test harness, worth as much as the rest: **`emu.setInput` must be
called from `inputPolled`, not `endFrame`** - from `endFrame` it lands after the
console has latched. That made a working port look like it ignored the
controller. Checking the same harness against the HiROM ROM, where input
demonstrably works, is what showed the test was wrong rather than the port.

### What is left

`ppu_wait_nmi()` is the whole seam. It polls `HVBJOY`, then flushes scroll,
CGRAM, VRAM, OAM and CHR and reads the pads - every one of which is S-CPU work.
The split is:

* **the mailbox** (`IRamShared`, 2KB): `oam_buf` 544B, `PAL_BUF` 64B, the VRAM
  queues 512B, the column slots 128B, CHR descriptors and the handshake. About
  1.3KB of the 2KB, which fits alongside the direct page.
* **`col_ring`** (2KB of column data) stays in BW-RAM; the S-CPU DMAs it through
  its own `$6000` window, which `SBMAP` points independently of the SA-1's.
* ~~the handshake~~ - done, above.

What the S-CPU's `scpu_frame` loop still has to gain is the pushing: scroll,
CGRAM, the VRAM queue, OAM and the budgeted CHR upload. All of it is register
and DMA work, so it goes in `src/sa1_boot.s` beside the loop rather than being
compiled - keeping both processors out of one C runtime's direct page and stack
is worth more than the convenience.

Until then nothing is drawn: the game paces correctly at 60Hz against a blank
screen.

## 6. Build and check

```sh
sh tools/build_sa1.sh
"C:/mesen2/Mesen.exe" --testrunner out/famidash-sa1.sfc       tools/verify_sa1.lua
"C:/mesen2/Mesen.exe" --testrunner out/famidash-sa1-bench.sfc tools/verify_sa1_bench.lua
```

Or all of them at once:

```sh
sh tools/verify_sa1_all.sh
```

```
verify_sa1             RESULT OK - SA-1 boots and shares I-RAM with the S-CPU
verify_sa1_bench       RESULT SA-1 1.73x with code in ROM, 2.92x with code in I-RAM
verify_sa1_c           RESULT OK - Calypsi C runs on the SA-1 with its data in BW-RAM
verify_sa1_rommap      RESULT 29 of 29 probed addresses map to ROM
```

Verdicts land in `out/sa1_probe.txt` and `out/sa1_bench.txt`. The build also
emits `out/famidash-sa1-base.sfc` — the same image with the header patched to a
plain FastROM cartridge, which is the only way to time the S-CPU run against the
clock the port actually ships on.

The main port is untouched by all of this: `tools/build_game.sh` and every
existing verifier still run as they did.
