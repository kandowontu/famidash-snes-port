# M2.23 — 16x16 OBJ mode: built, measured, and retired

16x16 OBJ mode has been "the structural fix for the sprite budget" in this
project's notes since M2.15. It was built here, end to end, and the measurements
say it is the wrong lever for the frame rate. Nothing from it is in the tree; this
is the record of why, so it is not proposed a fourth time.

---

## 1. What was built

Two halves, both working:

**A CHR re-layout.** A 16x16 OBJ does not take four arbitrary tiles: it takes
`N`, `N+1`, `N+16`, `N+17` in the 16-wide OBJ tile grid. Linear order puts an NES
8x16 sprite's two halves at `N` and `N+1` — side by side, so a 16x16 covering them
would be half of the wrong sprite. `snes_m0.obj_pair_layout()` (kept, unused)
reorders them so sprite `k` sits at

```
top    N = 32 * (k >> 4) + (k & 15)
bottom N + 16
```

which fills the grid in row pairs and makes any two consecutive sprites a valid
2x2 block. `oam_spr.s` mapped tile bytes through the same rule and
`gen_gamemode_expect.py` through it again as an independent oracle; all three
agreed and every sprite check passed.

**Runtime pairing in the walker.** `shim_meta_run` looked ahead one metasprite
entry and emitted a single 16x16 OBJ when the pair shared a row, sat 8 pixels
apart, shared attributes, and named consecutive sprites. It worked: **27.0 → 21.0
OAM entries per frame on `cycles`, a 22% reduction**, with the OBJ size bit set in
the OAM high table.

---

## 2. Why it is not in the tree

### 2.1 It made the walker slower

| `shim_meta_run`, instructions per game frame | merge off | merge on |
| --- | --- | --- |
| `cycles` | 1713 | **1755** |
| `xmaschallenge` | 1272 | **1370** |

The per-entry lookahead is four far-indirect reads of the next quadruplet plus
comparisons — about 25-30 instructions — and it runs on every entry, while only
about one in eight merges. Saving one 4-byte OAM write is worth about 10. The
frame rate confirmed it: `cycles` 84.6% with the merge off, 84.9% with it on.

Deciding the pairing OFFLINE (a spare bit in the metasprite attribute byte, which
has three free) would cut the test to three instructions and was the obvious next
step. It is not worth taking, for the reason below.

### 2.2 The ceiling is about 3% of the walker, not 20% of the frame

This is the part that was wrong in the plan for three milestones.

**16x16 mode reduces OAM ENTRIES. OAM entries are a PPU per-scanline resource,
not CPU time.** The walker's cost is per METASPRITE ENTRY: both halves of a
merged pair still have to be read from the table, sign-extended, positioned,
culled against the screen edges and converted to a SNES attribute. Merging only
removes the second entry's four-byte *write*.

On `cycles`: 6 fewer OAM entries per frame, about 10 instructions each, against
1755 instructions in the walker — **3.4%**, or under 0.5% of the frame. The 22%
entry reduction is real and buys nothing in CPU time.

What it WOULD buy is headroom against the SNES's 32-sprites/34-tiles-per-scanline
limit. That is a real problem on the levels with 80-90 live entries, and it is a
sprite DROPOUT problem, not a frame rate one. If dropout is ever observed, this is
the fix, and the measurements above say what it costs.

### 2.3 `xmaschallenge` was not caused by any of this

Level 37 runs at 23.4% of 60Hz and reads as a stall. With the merge disabled it
is 23.7%, and after the whole change was reverted, 23.4% — so it predates this
work entirely. It is not reloading either: zero `init_rld` calls over 2820 video
frames, so those are real game frames taking four video frames each. It is the
worst level in the set by a wide margin and wants its own investigation.

Also worth knowing: `profile_instr.lua` counts game frames with an exec hook on
`ppu_wait_nmi`, which the level-load loop also calls, so it reported 88.7% for the
same level `verify_framerate.lua` measured at 23.9%. `everything_else` runs once
per gameplay frame and is the right hook.

---

## 3. What the numbers say to do instead

`shim_meta_run` is 5.7 calls per frame, 276 instructions per call, ~26 OAM entries
— about **60 instructions per OAM entry**, and a quarter to a third of the frame.
For hand-written 65816 that is high, and the cost is all per-entry setup:

* sign-extending `dx`/`dy` and adding the bias,
* the two 16-bit screen-edge culls,
* the NES-to-SNES attribute conversion,
* the tile-pair split.

That is the lever. It is in a file this port owns, it helps every level including
the ones with no mergeable pairs at all, and unlike 16x16 it reduces work rather
than moving it.
